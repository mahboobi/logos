# 04 — Identity and invites

> **Amended 26 Oct 2026 — key hierarchy corrected (decided with the user).**
>
> §6's `project_key → wraps → idea_key` is a **correctness bug**, not a
> simplification: anyone holding the project key can derive every idea key, so
> the "Selected ideas" grant in M1 controls nothing. A reviewer invited to one
> idea could read the whole project.
>
> **The decided model is hybrid:**
> - `project_key` covers project-level metadata and membership records only —
>   the cheap shared things every member needs.
> - **Each idea has its own independent content key**, not derived from and not
>   wrapped by the project key. Access to an idea is an explicit grant, sealed
>   per member per idea.
>
> Consequences that must be implemented together, not piecemeal:
> - An invite seals N idea keys, not one project key.
> - Removing a member rotates `project_key` plus only the idea keys that member
>   actually held — not every key in the project.
> - Granting access later is a new sealed grant in a signed commit, so it is
>   auditable in history.
> - Removal is **forward-only**. A member who already held an idea key can
>   still read everything they received before removal; rotation protects new
>   content only. The UI must not imply otherwise.
>
> See docs/11-identity-design.md for the vault, sealing and rotation detail.


## 1. What the Logos docs establish (verified 25 Oct 2026)

- **Logos Chat identity is ephemeral on testnet.** `chat_module.init()` creates a new account on every launch, so `get_address()` changes each time Basecamp restarts. Conversations and history are not persisted. Users exchange the hex address out of band to start a 1:1 conversation. ([Chat getting started](https://docs.logos.co/messaging/get-started/send-1-1-messages-logos-chat), [Chat module API](https://docs.logos.co/messaging/chat-module/build-logos-module-that-uses-chat-module-api))
- **Chat groups cannot remove members**, and adds commit asynchronously (can take minutes). Unsuitable as a membership list.
- **The glossary defines no user-identity or profile object** in Basecamp. Identity-like keys exist at the node level (node key → Peer ID for Delivery) and in LEZ (account keys; sealing keys). ([Glossary](https://docs.logos.co/get-started/glossary))
- **LEZ sealing keys** are ML-KEM-768 key pairs, one per wallet, used to seal a Group Master Secret to a member so they can derive a shared account. The wallet CLI cannot reprint an existing sealing public key. ([Shared private accounts](https://docs.logos.co/lez/accounts/set-up-shared-private-lez-account))

**Consequence:** OLB owns its own long-term identity. Delivery is the transport; Chat is optional and never authoritative.

## 2. OLB identity

Generated by `olb_core` on first run, stored encrypted in the module data directory (back-up/export flow in Phase 1b).

| Key | Algorithm | Purpose |
| --- | --- | --- |
| Signing key | Ed25519 | Signs records, commits, invites, approvals |
| Sealing key | ML-KEM-768 | Receives sealed project and idea keys |
| Inbox secret | 32 random bytes (derived) | Derives the private inbox topic tag |

Decision to confirm (`docs/08-open-questions.md`): generate OLB's own ML-KEM key vs reuse the LEZ wallet's sealing key. Default: **own key**, because the wallet cannot re-export its public key and wallet keys also control funds.

### 2.1 Open Labbook ID (the string users copy)

```
olb1:<base64url( CBOR {
  v: 1,
  name: "Rui Santos",            // self-declared, unverified
  orcid: "0000-…" | null,         // self-declared, unverified
  sig_pk: <32 bytes Ed25519>,
  seal_pk: <1184 bytes ML-KEM-768>,
  inbox: <16 bytes inbox tag>,
  created: <unix seconds>,
  self_sig: <Ed25519 signature over all fields above>
}) >
```

- Length ~1.7 kB of text. The UI shows it truncated with "Copy my ID"; QR is out of scope for now.
- **Fingerprint** = first 12 bytes of `SHA-256("olb-fp-v1" || sig_pk || seal_pk)`, shown as 6 groups of 4 uppercase hex: `9C4F 2B71 D0A8 · 5E3C 11F9 E21A`.
- Parsing rejects bad version, bad signature, wrong key lengths. Display name and ORCID are always labelled unverified.
- Profile screen ("Copy my ID") is a small Phase 1 addition reachable from the node status box in the nav (not designed; use a simple panel).

## 3. Transport: inbox topics on Logos Delivery

- Each identity listens on an **inbox topic**: `/olb/1/inbox-<bucket>/proto`, where `bucket = first byte of inbox tag mod 16`. Many identities share each bucket topic (k-anonymity); messages carry an encrypted header, so only the recipient can tell a message is theirs.
- Messages are sealed to the recipient's ML-KEM key (KEM → HKDF → ChaCha20-Poly1305) and signed by the sender's Ed25519 key.
- Delivery Store keeps messages temporarily, so recipients offline for a short while still receive them. Long absences require "Resend".
- Verify whether publishing requires an RLN membership on testnet (`docs/08-open-questions.md`).

## 4. Invite by Open Labbook ID

```
Inviter (lead)                                     Invitee
  paste OLB ID ─► parse, verify self_sig
  show fingerprint; user confirms out of band
  choose role + idea access
  build InviteEnvelope:
    project_id, project_name, role, idea_ids,
    project_key(vN) and idea_keys sealed to seal_pk,
    inviter sig_pk, note (encrypted), expiry,
    invite_id, signature
  publish to invitee inbox topic ───────────────►  receive, verify inviter signature
  members: invite "pending · sent"                 show "Join {project}?" prompt with inviter fingerprint
                                                   accept ─► unseal keys, store, subscribe to project sync topic
                     ◄─────────────────────────── publish InviteAccept {invite_id, sig} to project topic
  core verifies, adds member, writes commit
  "Add {name} as {role}" (signed by inviter; accept sig attached)
  status ─► "Accepted, key installed"
```

States in `invites.list()`: `sealed`, `sent` (handed to Delivery), `received` (invitee node acknowledged with a signed receipt), `accepted`, `declined`, `expired` (default 14 days), `revoked`.

## 5. Invite by one-time code

```
Lead: create code  ── code = "OLB-" + Crockford-base32(10 random bytes), grouped 4-4-4-4
                      e.g. OLB-7Q4M-K2XD-93RB-FT5W. FOUR groups, not three:
                      10 bytes is 80 bits and needs 16 base32 symbols. The
                      three-group example this line used to carry was only 60
                      bits, so any UI mock showing three groups is wrong.
      store {code_hash, role, idea_ids, expiry, uses_left}
      subscribe to /olb/1/join-<H(code)[0] mod 16>/proto
      share code out of band
Newcomer: Join a project → paste code
      derive K = HKDF(code, "olb-join-v1"), tag = H(code)
      publish JoinRequest {tag, ENC_K(own OLB ID, note), sig}
Lead: core matches tag, decrypts with K, verifies the OLB ID
      Members › Pending invites shows "Redeemed by {name} · key {fingerprint}" + Review
      Review opens M1 at step 3 with Approve; lead confirms fingerprint out of band
      on approve: same InviteEnvelope as §4, sent to the requester's inbox
```

Codes are single-use by default; expire after 24 h / 48 h (default) / 7 d; "Make a new code" revokes the old one. Rate-limit join requests per code (5 per hour) to stop guessing; 80-bit codes make guessing impractical anyway.

## 6. Roles, access and key hierarchy

```
project_key (v3)  ── wraps ──►  idea_key[lid], idea_key[comp], …
member gets: project metadata key + only the idea keys in their access list
```

- Reviewer "Selected ideas" = only those idea keys are sealed to them.
- Widening access later = seal additional idea keys (a commit "Grant {name} access to {idea}").
- Role changes = signed commit; enforcement of write permissions happens in every member's core when validating incoming commits (reject commits from a Reviewer that edit records).

## 7. Removing a member and key rotation

1. Lead removes member → commit "Remove {name}".
2. Core generates project_key v(n+1) and new idea keys for every idea the removed member could read.
3. New keys are sealed to each remaining member and sent via inbox.
4. New records use new keys. Old records stay readable by those who had them (documented in UI: "They keep what they already had, but cannot read anything new.").
5. Members › Project key shows "Version n+1 · last rotated {date}".

## 8. Replica nodes

`olb_replica` holds a sealing key too but receives **no content keys**. It receives a signed "replicate project {id}" grant and the list of CIDs (and snapshot CIDs) to pin. It can serve ciphertext only.

## 9. Security notes for implementation

- Never auto-accept invites; always show inviter fingerprint.
- Constant-time compare for MACs and tags.
- Zeroize key material in memory where the crates allow.
- Replay protection: `invite_id` + expiry; reject duplicates.
- Display names are untrusted input; escape them in QML text.
